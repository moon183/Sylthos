# Sylthos 四人七天答辩筹备计划

编制日期：2026年10月25日。以下按连续七天筹备，D1 为10月25日，D7 为10月31日；实际答辩日期和可投入时间确认后整体平移。本计划为分工初稿，A至D暂代姓名，尚不代表功能已经完成或团队已经认领。

建议两人负责开发，一人负责测试与演示，一人负责PPT与讲稿。PPT从第一天开始，第四天形成完整初稿，第五天冻结功能范围，最后两天用于真实彩排、修复和备份。

## 一 本周交付范围

**基础必交。** 保证现有手势控制、校准、练习、自定义手势、离线字幕和彩排统计能在答辩电脑上运行；交付完整运行目录、答辩PPT、逐页讲稿、演示视频和真实测试记录。

**新增重点。** 在现有校准上增加个人档案与参数切换；提供基于PPT正文和备注的演前建议，输出逐页重点、时间安排和模拟问题。两项分别由A、B负责，D3必须拿出最小可演示版本。

**演后复盘保底。** 使用现有彩排时长、指令分发和逐页停留数据形成报告；若B的演前建议已经稳定，再增加基于这些数据的AI解读。没有语音与页码对齐数据时，不生成内容遗漏、口头禅或讲述质量的结论。

**加分项。** 带采集时间的转写记录、逐页内容复盘、两次彩排比较。D4仍未跑通即移入后续展望，不挤占测试与材料时间。

**本周暂不安排。** 持续自动学习、复杂多Agent、观众情绪推断、完整音视频分析、所有图表的自动理解、现场实时AI指导。这些范围不作为本周交付承诺。

本计划拟新增在线演讲分析能力，当前尚未实现；正式实施时需要同步更新SPEC中的在线API范围，沿用用户自行配置凭据的方式，并明确哪些材料会发送给服务端。

## 四 每天怎样对齐

每天约15分钟同步，按“今天交了什么、证据在哪、遇到什么阻塞、明天交什么”交流。C维护问题单，A确定技术修复顺序，D同步修改PPT和讲稿口径。

新增功能与修复必须更新相关测试并提交Git。实测反馈引发的修复须在tests中补失败场景回归。每次提交只包含自己的修改，不覆盖现有个人配置、模型或样本。功能完成必须同时满足代码可运行、相关检查通过、演示步骤可重复。

同一时段不要由多人改同一个GUI入口文件；A与B先约定接口和修改区域，再集成。每天保留一个可运行版本，未经集成验证的开发版本不替换演示包。

## 五 测试与证据采集

C负责组织，A和B配合解释与修复。以下数量是建议的试验安排，不是已经完成的结果，也不能据此声称广泛适用。

| 对象 | 建议做法 | 保存内容 |
|---|---|---|
| 个人校准 | 四人分别做默认参数与个人参数测试；每条件建议20次独立翻页动作；另记录普通比划 | 成功数与总数、漏识别、重复触发、自然比划误触次数及观察时长 |
| 测试公平性 | 校准动作与验证动作分开；记录距离、光线、设备和先后顺序；可交替两种条件顺序 | 条件说明与原始逐次记录，不能只留下最好的一组 |
| AI演前建议 | 准备至少3份不同结构PPT，含文字页、图表页和备注；检查页码和建议依据 | 输入版本、输出报告、人工核对问题及处理结果 |
| 彩排报告 | 用实际演讲记录核对时长和页码；无转写时只报告操作与节奏 | 原始日志、报告、未知页码区间；分发不等于PPT执行成功 |
| 运行交付 | 在实际答辩电脑打开完整分发目录，确认PPT、相机、麦克风和模型 | 环境清单、验收记录、版本号、完整演示视频 |

无法获得精确响应延迟时，先不填毫秒数；如用视频估计，应写明起止事件、视频帧率及测量误差。四位团队成员的结果只能描述这四人的本次测试，不能当成陌生人泛化实验。

## 七 演讲与现场协作

暂按口头讲解8分钟、软件演示2分钟准备，属于排练假设，须以学校实际时长为准。D主讲，C操作并处理设备，A回答算法与架构，B回答AI输入、分析依据和局限；如果只允许一人上台，其他成员承担台下保障并共同参与问答。

两分钟演示建议只保留三段：手势控制约45秒，个人校准或自定义手势约35秒，真实演前建议或彩排报告约40秒。字幕、主题和导航等放备用视频，不把每个功能都塞进现场。
